# ДЗ 9 · Крос-камерний трекер: один ID у двох дронах

До [заняття 9](../../lessons/09-mot-reid/). ≈ 3 години, 20 балів.

Ноутбук: [`03_mtmc_tracker_student.ipynb`](03_mtmc_tracker_student.ipynb), ядро **Python (cv-advanced)**.
GPU не обов'язковий: повний прогін — ≈ 1 хв на GPU і ≈ 2–5 хв на CPU.

Дані й ваги (≈ 1,3 ГБ) — один раз, з кореня репозиторію:
```bash
python tools/fetch_mdmt.py --seqs 46 48                          # MDMT: dev (46) і test (48), ≈ 0,9 ГБ
python tools/fetch_dino_models.py --models dinov2 --size base    # DINOv2-base, ≈ 350 МБ
```
HOTA рахує TrackEval із кореневого `requirements.txt`.

**Дані.** [MDMT](https://github.com/VisDrone/Multi-Drone-Multi-Object-Detection-and-Tracking) — два дрони одночасно знімають
ту саму сцену, і розмітка дає машині **той самий ID в обох дронах**: це готовий GT для крос-камерної метрики (на слайді — «GT у CVAT»;
розмітка MDMT і є CVAT XML). Пороги обираються на парі 46 (dev), міряються на парі 48 (test). Ліцензію автори не вказали:
академічне використання з посиланням на Liu et al., IEEE TMM 2023.

| Частина | Кроки | Слайди |
|---|---|---|
| 1 · трекер на камері | `n_init` / `max_age` у секундах → ByteTrack на кожному дроні → HOTA через TrackEval | «Життєвий цикл треку», «ByteTrack: пороги, які реально крутити» |
| 2 · візуальний опис | кропи з піксельним бюджетом → ембеддинг треклета (DINOv2 і колір HSV) → AUC / Rank-1 серед одночасно видимих | «Піксельний бюджет для ReID», «ReID: постановка, бекбони», «Доменний зсув і межі візуального опису» |
| 3 · час і простір | часове вікно → гомографія між дронами (SIFT + RANSAC, гейт за inliers) → відстань між треклетами в довжинах машини | «Крос-камерний трекінг: постановка», «Синхронізація часу та геоприв'язка», «Geo-MOT» |
| 4 · глобальні ID | злиття `вікно · s_geo · s_app^0.5` → гейт → угорський алгоритм → три зони порогів на dev | «Асоціація: вартість і призначення», «Метрики ReID і калібрування порогів» |
| 5 · чесний замір | ті самі пороги на test: HOTA по камерах і по мережі, ID persistence, хибні зшивки, частка й години оператора, мс по етапах → абляція | «Як міряти трекер на своєму домені», «Бюджет обчислень на edge-вузлі», «Домашнє завдання» |
| 6 · три провали | що / чому / що робити | «Коли трек уже мертвий», «Доменний зсув і межі візуального опису» |

У кожному з 16 TODO — один рядок або значення параметра; після кожного кроку `check()` показує ✅/❌. Таблиці з числами друкує
ноутбук; пишете висновки до 2.2, 4.2, 5.1, 5.2 і три провали в частині 6.

**Чому детектор симульований.** Готовий COCO-детектор (YOLO11m) на кадрах MDMT знаходить ≤ 4 % машин (надир, сутінки, 30–70 px),
тож детекції генеруються з GT із реальними прапорцями оклюзії MDMT — як у §7 демо 1. Свій детектор (зокрема Grounding DINO з ДЗ 6) — у бонусі.

**Здати** — **один архів** `dz9_<прізвище>.zip`, прикріплений в особистому кабінеті LMS: ноутбук з виводами
(Kernel → Restart & Run All, потім зберегти) із відповідями в клітинках «✍️» і `outputs/report.json`. Архів збирає остання клітинка
ноутбука (розділ «Здача»): впишіть прізвище в `SURNAME` і запустіть її після збереження. Окремі файли, посилання на диск чи
репозиторій не приймаються.

[`solution/`](solution/) — розв'язок для викладача. На RTX 5090 усі перевірки проходять за ≈ 1 хв. На dev кращий дескриптор — DINOv2
(AUC 0.84 проти 0.83 у кольору, Rank-1 лише 0.50 серед ≈ 69 кандидатів); гомографія між дронами кладе проєкцію на ту саму машину
з похибкою ≈ 0.09 довжини. Пороги `T_LOW = 0.45`, `T_HIGH = 0.5`: на test — 0 % хибних автоматичних зшивок, ID persistence 0.76 → 0.83
з оператором (9 % пар), HOTA по мережі 0.69, IDF1 0.79. Абляція на test: без геометрії persistence 0.07, без візуального опису — 44 % хибних
зшивок, без часового вікна — удвічі більше роботи оператору.
