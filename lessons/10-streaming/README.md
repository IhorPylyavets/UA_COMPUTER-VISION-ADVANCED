# Заняття 10 · Демо та ноутбуки

Усі ноутбуки працюють на одному комп'ютері зі справжнім GStreamer: відправник `appsrc → x264enc → RTP/UDP` (або MPEG-TS/SRT),
емулятор лінку на Python (ємність, затримка, джиттер, втрати, серії втрат) і приймач `udpsrc / srtsrc → avdec_h264 → appsink`.
Кожен кадр несе штрихкод зі своїм номером, тому вік кадру — це час прийому мінус час відправлення того самого кадру за одним
годинником. Датасети не потрібні: сцени синтетичні й детерміновані.

Файли `streamlab.py`, `streamcore.py`, `gstworker.py` і `panels.py` мають лежати поруч із ноутбуками. `streamlab` запускає
GStreamer в окремому процесі (`gstworker.py`), тож ноутбук сам `gi` не імпортує: pip-колеса numpy / pyzmq і системні бібліотеки
GStreamer на частині збірок падають в одному процесі. Сцена, емулятор і Калман — у `streamcore.py`, стиль графіків — у `panels.py`.

## Веб-демо

Самодостатні HTML-сторінки: досить відкрити файл у браузері, сервер і GStreamer не потрібні. Без інтернету лише шрифт IBM Plex
заміниться системним. Це моделі з повзунками до тих самих слайдів, що й ноутбуки: ноутбук показує, як є на справжньому x264 і
GStreamer, а веб-демо — чому так і що буде, якщо змінити параметри. Зручні для самостійної роботи й як запасний варіант, якщо на
лекційній машині не запускається GStreamer.

## Середовище

Ноутбуки відкриваються в звичному ядрі **Python (cv-advanced)**. Сам GStreamer (PyGObject і плагіни) у `cv-advanced` не входить
(див. коментар у кореневому `requirements.txt`), тому `gstworker.py` запускається окремим інтерпретатором. `streamlab` бере перший,
у якому імпортуються `gi`, numpy і scipy: змінна `STREAMLAB_PYTHON` → інтерпретатор ядра → conda-середовище `cv-streaming` поруч із
`cv-advanced` → системний `/usr/bin/python3`. Якщо жоден не підходить, перша клітинка скаже, що саме перевірено.

**Linux, conda-forge (без sudo):**

```bash
conda create -n cv-streaming -c conda-forge --override-channels python=3.11 pygobject gstreamer gst-plugins-base \
    gst-plugins-good gst-plugins-bad gst-plugins-ugly gst-libav numpy scipy matplotlib ipykernel
```

Так ставиться GStreamer 1.28 з `x264enc`, `avdec_h264`, RTP і MPEG-TS — досить для ДЕМО 01, 02, 04 і RTP-частини ДЕМО 03.
**SRT у conda-forge немає:** `gst-plugins-bad` там зібраний без libsrt, і ДЕМО 03 пропускає SRT-рядок з повідомленням.
Для SRT на лекції — системний GStreamer Ubuntu, де `srtsrc` / `srtsink` є в `gstreamer1.0-plugins-bad`:

```bash
sudo apt install python3-gi python3-numpy python3-scipy gir1.2-gstreamer-1.0 gir1.2-gst-plugins-base-1.0 \
    gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly gstreamer1.0-libav
/usr/bin/gst-inspect-1.0 x264enc avdec_h264 srtsink > /dev/null && echo "плагіни на місці"
export STREAMLAB_PYTHON=/usr/bin/python3     # або просто не створюйте cv-streaming — системний python3 перевіряється останнім
```

Через pickle між процесами їздять масиви numpy, тому numpy у воркері не має бути старшим за numpy ядра (numpy 2 читає pickle
numpy 1, навпаки — ні). Windows і macOS — через WSL2 / Linux-ВМ.

Перша клітинка кожного ноутбука друкує версію GStreamer і те, чи є в appsink `leaky-type` (з'явився в 1.28; до того —
`max-buffers` + `drop`). Якщо в `PATH` є conda з власним GStreamer, перевіряйте плагіни саме системним `/usr/bin/gst-inspect-1.0`.

Числа залежать від завантаження CPU: на однопроцесорній машині частина затримки — конкуренція за процесор.

## Розділи ноутбуків (посилання зі слайдів LIVE DEMO)

**ДЕМО 01:** §1 відправник і приймач без навантаження · §2 appsink без ліміту і повільний детектор · §3 Latest(1) · §4 трекер на нерівному кроці.
**ДЕМО 02:** §1–2 енкодер і лінк · §3 розмір кадру і затримка кадру · §4 серія втрат і відновлення.

## Очікувані числа (GStreamer 1.28.8, conda-forge)

Числа з кількох прогонів на одній машині; там, де вони помітно стрибають між прогонами, — діапазон.

- ДЕМО 01: без детектора вік кадру p50 ≈ 3 мс; без ліміту в appsink вік росте на 0.53 с щосекунди (модель — 0.524),
  за 10 с останній кадр старший за 5.4 с; Latest(1) — p50 ≈ 19 мс, p99 ≈ 36 мс, дропнуто ≈ 157 кадрів із 300 (детектор ≈ 14 Гц).
  На кадрах із §3 обидва Калмани в межах гейта; із зупинками детектора частка прогнозів поза гейтом: dt з PTS ≈ 5 %, dt = 1 ≈ 16–18 %.
- ДЕМО 02: p99 затримки кадру — ≈ 265 мс з IDR проти ≈ 38 мс з intra-refresh (p50 обох ≈ 30–33 мс); «ключовий» / інші ≈ 10 для GOP
  і ≈ 1.6 для intra-refresh. Після серії втрат чиста картинка через ≈ 450 мс (чекаємо IDR), ≈ 80 мс (PLI) і ≈ 1400 мс (intra-refresh).
- ДЕМО 03 (лише RTP: у conda-forge немає SRT): p50 ≈ 64 мс у всіх трьох конфігураціях. JB 20 без втрат — p99 160–330 мс і лише
  10–55 % чистих кадрів (найбільше стрибає між прогонами); JB 80 — p99 ≈ 155 мс, 99–100 % чистих; JB 80 на 2 % втрат — p99 225–440 мс,
  показано 75–95 % кадрів, чистих 5–15 %. SRT 240 мс на системному GStreamer 1.24.2 — p50 ≈ 355 мс, 91 % чистих.
- ДЕМО 04 (x264 з `threads=1`, тому числа відтворюються до відсотка): recall на сирих кадрах 100 %;
  1600 / 800 / 400 / 200 / 100 кбіт/с — 92 / 90 / 88 / 85 / 47 % (за розміром цілі — як на слайді 22); поріг, підібраний на
  200 кбіт/с (9), піднімає recall з 85 % до 96 %, але на сирих кадрах дає ≈ 4 хибних спрацювання на кадр.

ДЕМО 04 зберігає підсумок у `outputs/demo4_results.json` поруч із ноутбуком (тека в `.gitignore`).
